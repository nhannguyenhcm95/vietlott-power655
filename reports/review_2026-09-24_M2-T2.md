## 1. Deviations self-reported by data-engineer — ruling

1. **`Finding` in `src/validation/findings.py`, re-exported from `reporting`.** ACCEPTABLE. Confirmed it avoids a circular import (`lineage.py`/`reconcile.py` need `Finding` without importing `reporting.data_quality`, which imports them). `src/reporting/data_quality.py` imports `Finding` from `src.validation.findings` directly; no functional difference from the design, which only specifies the dataclass, not its file.

2. **`known_issues.file` findings (proposed/expired/unused) computed after the other checks, merged back.** ACCEPTABLE — necessary. `known_issue_unused`/`known_issue_rule_unused` require the total match count across *all* checks (reconcile.sources included), which is only known once every check has run. `_finish_known_issues_file` in `src/reporting/data_quality.py:153` does this and re-sorts/re-derives status correctly. Verified real output: `known_issues.matched = {chronological_order: 1, reconcile.only_left: 1}` (see §3).

3. **`draw_weekday`/`main_sorted`/`draw_id_continuity` findings surfaced only via `curated.ranges`, not also under `coverage.gaps`/`quality_log.open`.** ACCEPTABLE, with a note. Design §1.4's "check" column lists three check_ids for this row, but `RuleSpec.check_id` in `known_issues.py` is otherwise unused by the report (confirmed by grep — it plays no role in KI acceptance logic, only documentation). `quality_log.open`'s handling of these rule names is generic (`Finding(source, row.draw_id, None, row.rule, ...)`, `src/reporting/data_quality.py:497`), so if any of these three rules were ever logged historically in `quality_log.csv`, they would still surface under `quality_log.open`, not be hidden. `coverage.gaps` genuinely omits `draw_id_continuity` (only `first_draw`/`draw_cadence`), which is a minor placement choice, not a suppression — the finding still appears under `curated.ranges`. No known-issue-hiding risk here.

4. **RESOLVED `quality_log` items listed at INFO.** ACCEPTABLE. Design §1.3 only says a resolved item is "listed only," without specifying a level. INFO is the correct choice since it keeps the item visible (`accepted=False`, still in the JSON/md) while not affecting `_status_of`/unaccepted counts, which only consider FAIL/WARN. This matches "listed only" without silently affecting status.

5. **`reconcile.mirror_lag` uses a sequence index over `only_left` ids above the mirror max, not literally `draw_id − mirror_max`.** ACCEPTABLE. The design never states the formula as `draw_id − mirror_max` — it only requires that O5's observation holds (lag 1 at 20:00, lag 0 at 08:30) and the INFO≤3/WARN>3 threshold. `assess_reconcile` (`src/validation/reconcile.py:101–111`) iterates `rep.only_left` in ascending numeric order (ids are zero-padded strings, so lexicographic sort = numeric sort) and assigns lag = 1-based position among ids above `mirror_max`. This is numerically identical to `draw_id − mirror_max` whenever the official ids above the mirror max are contiguous (the normal case — any real gap would already be flagged separately by `coverage.gaps`/`curated.ranges`). `test_mirror_lag_info_then_warn` in `tests/test_quality_report.py` exercises both the INFO and WARN branches.

6. **Test-coverage table vs design §1.9 / audit finding 19 / re-audit N1–N9.** See §2 below. Two rules — `mirror_shrink` and `known_issue_unused` — have **no test at all** (not even an equivalent-name test). Both are WARN-level, never-KI-acceptable rules that exist specifically to catch silent data loss / stale known-issue entries. Per the review brief, this is **REWORK**.

7. **Test count.** Confirmed: `python -m pytest` → **174 passed**, 0 failed/errored, consistent with 59 baseline + 115 new.

## Findings (numbered, for the required fix)

**F1 — MAJOR (REWORK).** `test_mirror_shrink_warn` (design §1.9, audit finding 19) does not exist anywhere in `tests/`. The `mirror_shrink` code path (`src/reporting/data_quality.py:439-449`, WARN, never KI-acceptable per §1.4) is completely unexercised — both the "shrink" and "no shrink" branches, and the "not evaluated when `received` is empty" guard. **Required fix:** add `test_mirror_shrink_warn` (or the R3-renamed `test_mirror_shrink_warn_exit10` if data-engineer prefers to align naming with M2-T3's refresh test) covering both trigger conditions (`max(received) < max(staged)`; staged not a subset of received) and confirming it is skipped when `received` is empty.

**F2 — MAJOR (REWORK).** `test_ki_unused_warn` (design §1.9, audit finding 19) does not exist. `known_issue_unused`/`known_issue_rule_unused` (`src/reporting/data_quality.py:153-181`) — the mechanism that detects a stale/no-longer-matching known issue, i.e. the known-issue safety net — is untested. **Required fix:** add a test with an active KI whose scope matches nothing (or only some of its rules) and assert `known_issue_unused` (WARN, whole-entry unused) and `known_issue_rule_unused` (INFO, per-rule unused) both appear as expected.

**F3 — MINOR.** `test_cli_quality_report_exit_codes` (tests/test_quality_report.py:113) only asserts exit 0 and exit 10 through the CLI; exit 30 (FAIL) is never exercised through `main(...)`, only indirectly via `build_quality_report`/`_report` helpers in the absent-input tests. The dict-lookup mapping in `src/cli.py:117` is simple, so risk is low, but the design explicitly names this test as covering "(0/10/30)". **Suggested fix:** extend the test (or add one line) asserting `main([...], paths=paths)` returns 30 for a FAIL scenario (e.g. missing curated files, or the blanked-approval WARN scenario elevated to FAIL by another absent input).

No other deviations rise to REWORK. Items 1–5 and 7 in the implementer's self-report are ACCEPTABLE as implemented, with the notes above. Real-data determinism, exit-code semantics for PASS/WARN, KI-001 correctness, and the never-acceptable integrity-rule vocabulary are all verified correct.
